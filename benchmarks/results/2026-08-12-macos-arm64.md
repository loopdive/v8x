# V8, QuickJS, and js2wasm — macOS arm64, 2026-08-12

Medians of five fresh processes per engine. Each footprint process retains 100
live instances; the steady slope is measured from instance 10 through instance
100. QuickJS and js2wasm factors are relative to real V8.

## Footprint and startup

| Metric | V8 | QuickJS | js2wasm |
| --- | ---: | ---: | ---: |
| Combined linked payload | 39.1 MiB | 4.5 MiB (8.7× smaller) | 2.4 MiB (16.6× smaller) |
| One live instance RSS (shared init included) | 7.9 MiB | 9.2 MiB (1.2× larger) | 1.6 MiB (4.9× smaller) |
| Steady RSS per additional instance | 1.0 MiB | 1.6 MiB (1.6× larger) | 40.9 KiB (25.8× smaller) |
| Steady virtual address space per instance | 517.4 MiB | 4.5 MiB (115.5× smaller) | 4.1 GiB (8.0× larger) |
| Steady module/isolate creation time | 314.0 µs | 3.1 ms (9.9× slower) | 43.0 µs (7.3× faster) |

The linked payload is a stripped benchmark executable. The js2wasm result
includes its 1.7 MiB compiler-free runtime plus one shared 0.7 MiB `.cwasm`
program artifact; it does not include the compiler or Cranelift.

The virtual-address row is not allocated guest memory or physical RAM. This
benchmark module has no linear memory: the 4.1 GiB js2wasm result is Wasmtime's
default WasmGC heap address reservation plus guard regions. Only touched pages
become resident, as reflected by the much smaller RSS measurements.

## Warm execution speed

Absolute values are elapsed time. Parentheses show the speed factor relative to
V8.

| Warm workload | V8 | QuickJS | js2wasm |
| --- | ---: | ---: | ---: |
| Export-call boundary (200,000 calls) | 31.0 ns/call | 44.2 ns/call (1.4× slower) | 15.0 ns/call (2.1× faster) |
| Numeric kernel (10,000,000 loop iterations) | 4.1 ns/iteration | 17.7 ns/iteration (4.3× slower) | 9.5 ns/iteration (2.3× slower) |

On this narrow numeric kernel, js2wasm is 2.3× slower than V8 and 1.9× faster
than QuickJS. The trivial typed Wasmtime export boundary is faster than the V8
and v8x/QuickJS call paths, but this row does not compare a Deno op: each engine
uses its native host API. The kernel makes the one-time export lookup negligible
but remains a microbenchmark, not application or HTTP throughput.

All three engines returned 42 for every no-op batch and 293,659 for every
500,000-iteration kernel call. The runner rotated engine order between repeats.
Unrounded per-process measurements are retained in the runner's
`target/engine-comparison/results.txt` output and feed the summary generator
directly.
