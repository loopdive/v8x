# V8, QuickJS, and js2wasm — macOS arm64, 2026-08-12

Medians of five fresh processes per engine. Each footprint process retains 100
live instances; the steady slope is measured from instance 10 through instance
100. QuickJS and js2wasm factors are relative to real V8.

## Footprint and startup

| Metric | V8 | QuickJS | js2wasm |
| --- | ---: | ---: | ---: |
| Combined linked payload | 39.1 MiB | 4.5 MiB (8.7× smaller) | 1.8 MiB (22.4× smaller) |
| One live instance RSS (shared init included) | 7.7 MiB | 9.1 MiB (1.2× larger) | 992.0 KiB (8.0× smaller) |
| Steady RSS per additional instance | 1.0 MiB | 1.6 MiB (1.6× larger) | 8.4 KiB (126.0× smaller) |
| Steady virtual address space per instance | 514.5 MiB | 3.4 MiB (150.3× smaller) | 0 B (no measurable increase) |
| Steady module/isolate creation time | 317.0 µs | 3.1 ms (9.9× slower) | 22.0 µs (14.4× faster) |

The linked payload is a stripped benchmark executable. The js2wasm result
includes its 1.7 MiB compiler-free runtime plus one shared 49.7 KiB `.cwasm`
program artifact. Its raw `wasm-opt -O4` output is 610 bytes. The deployed
payload does not include js2wasm, Binaryen, or Cranelift.

The virtual-address row is not allocated guest memory or physical RAM. After
js2wasm O4 and `wasm-opt -O4`, the numeric module has no linear memory, array,
or struct declarations. It therefore does not trigger Wasmtime's default 4 GiB
WasmGC heap reservation; the median steady virtual-address slope was 0 B.

## Warm execution speed

Absolute values are elapsed time. Parentheses show the speed factor relative to
V8.

| Warm workload | V8 | QuickJS | js2wasm |
| --- | ---: | ---: | ---: |
| Deno `add_js`, runtime input (200,000 calls) | 33.1 ns/call | 63.5 ns/call (1.9× slower) | 12.6 ns/call (2.6× faster) |
| Deno `add_js`, constant inputs (200,000 calls) | 35.6 ns/call | 60.1 ns/call (1.7× slower) | 13.6 ns/call (2.6× faster) |
| Input-dependent mixed kernel (20,000 calls × 512 rounds) | 11,965.1 ns/call | 69,970.1 ns/call (5.8× slower) | 23,232.6 ns/call (1.9× slower) |

The two `add_js` rows adapt Deno's own
[`add_js` benchmark](https://github.com/denoland/deno/blob/1d4e6c1cb855b62a7fb572c6c138e4e8b4e7fa44/tests/bench/deno_common.js#L8-L12).
The runtime-input row keeps the operand dynamic for all engines. In the
constant-input row, js2wasm O4 pre-evaluates `addJS(1, 2)` and the final
`wasm-opt -O4` module returns the literal `3`; V8 and QuickJS receive the
original JavaScript.

The mixed kernel takes seed 123,457 from the host and performs 512 rounds of
arithmetic, modulo, and branching. The optimized Wasm retains the input read
and complete loop, proving that row was not pre-evaluated. js2wasm is 1.9×
slower than V8 and 3.0× faster than QuickJS on this workload.

All three engines returned 42 for the runtime-input add, 3 for the constant
add, and 786,699 for the mixed kernel. The runner rotated engine order between
repeats. Unrounded per-process measurements are retained in the runner's
`target/engine-comparison/results.txt` output and feed the summary generator
directly.
