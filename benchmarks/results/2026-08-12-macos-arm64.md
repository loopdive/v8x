# Engine footprint — macOS arm64, 2026-08-12

Three fresh processes per engine, each retaining 100 live instances. Values in
the comparison table are medians. The steady slope is measured from instance
10 through instance 100, not extrapolated from the first instance.

| Metric | QuickJS | js2wasm + Wasmtime | Difference |
| --- | ---: | ---: | ---: |
| Stripped benchmark executable | 4.492 MiB | 1.685 MiB | — |
| AOT program artifact | — | 0.656 MiB | — |
| Combined benchmark payload | 4.492 MiB | 2.341 MiB | js2wasm 47.9% smaller |
| First live instance RSS | 8.906 MiB | 1.562 MiB | js2wasm 5.7x smaller |
| Steady RSS per instance | 1.616 MiB | 39.5 KiB | js2wasm 41.9x smaller |
| Steady creation time | 3,052 us | 42 us | js2wasm 72.7x faster |
| Steady virtual address space per instance | 4.6 MiB | 4.0625 GiB | js2wasm reserves about 4.06 GiB/instance |

The virtual-address result is the important counterweight to the RSS result:
Wasmtime does not commit 4 GiB of physical memory per instance, but its default
WasmGC configuration reserves roughly 4 GiB of address space for every store.
That reservation can become the scaling limit before RSS does. QuickJS's
virtual-address slope was noisier than RSS (1.6–6.3 MiB across the three runs),
while js2wasm's reservation was stable.
